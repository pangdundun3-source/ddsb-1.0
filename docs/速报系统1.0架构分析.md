# 速报系统 1.0 架构分析

> 版本:v0.1
> 日期:2026-08-28
> 分析对象:当前代码仓库 + 白皮书目标架构(门户层 / 应用层 / 业务层 / 能力层 / 数据层)

---

## 一、分析结论速览

1. **当前仓库的本质**:速报系统的"统一入口门户",是一个纯前端 React 应用。四个业务终端(客户管理端 / 审核上报 H5 / 审核上报 PC / 应用管理端)是四个独立仓库,由启动脚本编排为"一套演示环境"。
2. **核心差距**:产品白皮书承诺的五层架构(门户 / 应用 / 业务 / 能力 / 数据),当前只落了"门户层 + 业务层的界面",能力层(权限服务、AI、文件、消息)与数据层均为**目标态,尚无实现**。
3. **资产闲置风险**:仓库内已有一套完整的"增强版门户"(终端卡片、详情抽屉、二维码、广播、帮助、四个终端模拟面板及类型化数据),但**当前实际渲染的是简化版入口页**,增强版组件未被引用——这是最值得优先解决的架构问题。
4. **商业化硬伤**:终端地址硬编码为本机端口、无统一登录与权限门禁、无后端数据,导致系统只能作为"演示 Demo"运行,无法支撑白皮书中的多租户、统计考核、审计等商业承诺。

## 三、分层架构分析

### 3.1 门户层(本仓库)

门户承担"统一入口 + 角色导航 + 状态呈现"职责。

**当前设计**:

- 简化版:四张终端卡片,点击新标签页跳转;
- 增强版(未启用):用户/环境模型、终端卡片、详情抽屉、二维码入口、系统广播、快捷工具栏、帮助中心,以及四个终端的内嵌模拟面板(通过 `onBack` 返回门户,暗示"门户内嵌预览"设计意图)。

**问题**:

- 两套门户并存,增强版承载了产品白皮书的大量卖点(角色权限、终端健康度、广播、二维码),不接入等于白皮书与产品脱节;
- `TERMINAL_URLS` 硬编码 `localhost:3000~3004`,换环境(测试/预发/生产)需改代码;
- 权限模型(`UserRole`、`allowedTerminals`)在类型层面存在,但简化版门户没有任何权限门禁,任何角色都能看到所有终端。

### 3.2 应用层(六大中心)

报送 / 审核 / 统计 / 考核 / 消息 / 系统管理在代码中以"终端模拟面板 + 门户组件"形式存在:

- 报送中心:H5 面板(拍照、GPS、离线暂存语义);
- 审核中心:PC 面板(批量裁决、质检);
- 客户中心:V8 客户管理面板(客户档案、配额池、流水);
- 系统管理:MT 面板(密钥、权限树、审计语义);
- 统计 / 考核 / 消息:以门户的广播、快捷工具栏等组件弱体现,无独立中心。

**问题**:六大中心是白皮书的产品骨架,但当前分散在各自终端的 mock 组件里,没有统一的数据契约与状态机,后续"统计/考核/消息"要复用数据时无从下手。

### 3.3 业务层(四端)

四端为独立仓库,靠端口区分。优点:职责清晰、可独立演进、支持"按端售卖";缺点:

- 无共享设计系统与组件库,视觉/交互漂移风险高;
- 无共享权限与登录,门户无法做真正入口控制;
- 无共享 API 网关,外部系统接入没有统一通道(与 MT 端"应用网关"定位冲突)。

### 3.4 能力层(空缺)

白皮书承诺的 AI、多模态分析、文件、消息、权限服务均未实现。依赖中虽有 `@google/genai`,但**未发现任何调用代码**,`GEMINI_API_KEY` 仅停留在环境变量样例。这是产品"AI 生成草稿、OCR 识别"卖点的最大缺口。

### 3.5 数据层(空缺)

无数据库、无缓存、无搜索、无日志存储。现有"统计"全部来自前端 mock。意味着:白皮书的"全程可追溯、统计考核、审计留痕"在当前架构下无法成立。

## 四、关键机制分析

### 4.1 终端发现与路由

现状:静态配置数组 + 硬编码地址;增强版有更丰富的元数据(版本、状态、指标、快捷入口)但未启用。

建议:终端元数据"配置化 + 可发现",门户从配置中心/接口拉取,支持按环境注入地址、按角色过滤、按状态展示。

### 4.2 权限模型

现状:类型层定义了 `UserRole` 与 `allowedTerminals`,但未形成门禁;`Environment` 枚举未使用。

建议:建立"角色 × 终端 × 数据范围"权限矩阵,至少先在门户实现终端级门禁(无权限不可见、不可进),再演进为统一 RBAC 服务。

### 4.3 状态管理

现状:仅组件内 `useState`,无全局状态、无路由、无跨端通信。

建议:门户内部先引入轻量全局状态(用户、环境、收藏、广播),暂不需要重量级方案;跨端会话由统一登录(SSo/SSO)解决,而非前端通信。

### 4.4 构建与运行

现状:单仓库 Vite 构建,`dev:all` 编排多进程;无生产部署说明;`index.html` 标题仍为 AI Studio 模板占位("My Google AI Studio App"),README 也是模板。

建议:补充生产构建与部署拓扑(静态托管 + 网关),统一门户与各端的环境变量注入。

## 五、问题清单(按优先级)

### P0(阻碍产品成立)

1. 能力层与数据层空缺,白皮书核心承诺(统计、考核、审计、追溯)无法兑现。
2. 无统一鉴权与权限门禁,门户只是"链接合集",不是"统一入口"。
3. 终端地址硬编码本机端口,无法部署到任何真实环境。

### P1(资产浪费与体验)

4. 增强版门户(portalData + 全套组件 + 四端模拟面板)未接入,与简化版并存,存在版本漂移。
5. AI 依赖已声明但无任何调用,OCR/AI 草稿卖点悬空。
6. 四端仓库无共享设计系统与共享数据契约,长期维护成本高。

### P2(工程整洁度)

7. `index.html`、README 等仍为 AI Studio 模板痕迹。
8. 无测试、无 CI、无环境配置管理。
9. 白皮书生成脚本(`_make_whitepaper.py`)依赖本机图片路径,不可复现。

## 六、演进路线建议

### 阶段 0:资产归位(1 周内)

- 将增强版门户设为默认渲染,简化版作为 fallback 删除或降级;
- 统一使用 `types.ts + portalData.ts` 作为门户数据契约;
- 清理模板痕迹(index.html 标题、README)。

### 阶段 1:门户闭环(2~4 周)

- 终端地址环境化(测试/预发/生产注入);
- 门户接入登录态与终端级权限门禁;
- 消息中心(广播 → 站内信)从 mock 走向可配置;
- 补充门户到各端的统一跳转参数(会话、来源、深链)。

### 阶段 2:能力层落地(1~2 月)

- 建设统一网关与鉴权服务(四端共用的登录、权限、审计);
- 落地 AI 服务(OCR 识别、草稿生成)作为独立能力,前端只做调用;
- 建设报送/审核主链路的数据层(业务库 + 状态机 + 留痕);
- 统计 / 考核 / 消息中心基于真实数据上线。

### 阶段 3:SaaS 化(2 季度+)

- 多租户与计费体系;
- OpenAPI 与第三方接入管理(承接 MT 端定位);
- 运营分析看板与客户成功工具。

## 七、架构决策建议(供评审)

| 决策点 | 建议 | 理由 |
| --- | --- | --- |
| 门户与四端是否合并 | 保持多仓库,门户作为独立应用 | 支持按端售卖与独立交付 |
| 共享能力如何沉淀 | 独立网关 + 服务,不做前端共享库优先 | 权限/审计/AI 是后端职责 |
| 四端设计一致性 | 先建轻量设计令牌(色板/字体/间距) | 成本低、见效快 |
| 数据层起步 | 先做报送/审核主链路库 | 与 P0 主流程一致,最小闭环 |
| AI 接入方式 | 服务端封装,前端仅接 REST | 密钥安全、可计量、可审计 |
