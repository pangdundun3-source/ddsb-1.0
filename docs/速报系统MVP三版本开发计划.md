# 速豹系统 MVP 三版本开发计划（1.0 / 2.0 / 3.0）

> 版本：v0.2  
> 日期：2026-10-09  
> 依据：《需求功能确认单（速豹系统 1.0，v1.0.0，产品经理：王飞飞）》为 1.0 范围的唯一依据；2.0 / 3.0 参考《点点速报系统商业版产品白皮书》与四个业务端的现有原型。  
> 定位：本文是「版本边界 + 功能清单」级别的开发计划，用于范围对齐与排期；不含接口级技术设计。  
> 范围：仅含 4 个业务端与后端平台能力，**不含门户**（门户是开发者演示聚合页，不是交付物）。

## 一、本次调整说明（v0.1 → v0.2）

本版以需求功能确认单为准，重新划定 1.0 的边界，主要变化如下：

| 变化 | v0.1 | v0.2（按确认单） |
| --- | --- | --- |
| 登录方式 | 1.0 账号密码，微信授权放 2.0 | **1.0 即为微信体系登录**：H5 微信授权 + 激活绑定；PC 与客户管理端微信扫码；MT 企业微信扫码 |
| 多机构 | 1.0 单机构，多机构放 2.0 | **1.0 即支持多机构**：MT 开通机构、机构级配置；客户管理端账号可关联多个机构并切换 |
| 配置体系 | 1.0 只有模板与流程 | **1.0 建成"平台默认 → 机构配置"两级**：模板、审核流程、审核打分规则、激活码、数据字典 |
| 审核打分 | 未单列 | **1.0 客户管理端审核时打分**，打分规则可配置（3.0 考核直接使用） |
| 人员分组 | 2.0 | **1.0** |
| 撤回 | 撤回后落点待定 | **取消撤回，改为删除**：待审核、被驳回的报送可删除 |
| 首页 | 1.0 各端都有首页看板 | **各端首页看板统一放 3.0**；H5 首页在 1.0 只承担"新建报送"入口 |
| 客户管理端报送管理 | 1.0 | 移到 2.0（1.0 客户管理端只做审核与管理配置） |
| H5 / PC 转办 | 1.0 | 移到 2.0（1.0 审核只有通过、驳回） |

**不变的约束：** 首页、统计、考核放在 3.0（系统日志、消息公告通知同样在 3.0）；门户不纳入；草稿箱不恢复。

## 二、版本策略总览

| 版本 | 一句话定位 | 核心命题 | 完成标志 | 建议周期 |
| --- | --- | --- | --- | --- |
| **1.0 MVP** | 多机构可上线的报送审核闭环 | 登录真起来、配置能下发、流程跑通、打分落库 | MT 开通机构 → 客户管理端完成配置 → 一线人员 H5 激活并上报 → 逐级审核、打分 → 上报人看到结果 | 8~10 周 |
| **2.0** | 审核提效与数据沉淀 | 审核更快、数据能沉淀可用、AI 形成效率差 | 数据仓库、批量匹配、转办、查重首发、AI 辅助接入主流程 | 8~10 周 |
| **3.0** | 运营治理与商业化 | 数据能看、人员能考、行为可审计、信息能触达 | 首页看板、统计、考核、日志、消息公告上线，具备商业化交付能力 | 8~12 周 |

### 三条贯穿原则

1. **后置的是展示层，前置的是数据层。** 首页、统计、考核能放到 3.0，前提是 1.0 就把状态流水、审核打分、组织归属、时间戳、操作埋点写进数据库。
2. **每个版本端到端可交付。** 1.0 结束就能完整跑通"开通机构 → 配置 → 激活 → 上报 → 审核 → 结果"。
3. **复用现有 UI，重写数据源。** 现有四端原型是画好的界面，工作量主要在"换数据源 + 补字段"。

## 三、1.0 MVP 功能清单（以需求功能确认单为准）

### 3.1 版本目标

实现全国各机构的组织架构人员管理、信息采集与审核流转：平台为机构开通服务并下发默认配置，机构管理员维护组织、人员和业务规则，一线人员在 H5 / PC 上报，审核人员逐级审核并打分，结果回到上报人。

### 3.2 开发顺序

确认单中的优先级在本计划里同时代表**开发顺序**：

- **P0（先做）：MT 应用管理端 + V8 客户管理端。** 机构、账号、组织、角色、模板、流程、打分规则、激活码、字典都在这两端产生，是上报和审核的前置条件。
- **P1（后做）：V8 上报审核端 H5 + V8 上报审核 PC。** 依赖 P0 产出的机构、模板与流程配置。

### 3.3 平台地基（与 P0 同步建设）

| 能力 | 内容 | 说明 |
| --- | --- | --- |
| 微信体系登录 | 微信网页授权（H5）、微信扫码（PC / 客户管理端）、企业微信扫码（MT），签发 Token | 四端共用一套身份；需提前申请公众号、开放平台网站应用、企业微信应用 |
| 激活与身份绑定 | 激活码 / 二维码 → 校验姓名、手机号 → 绑定机构与角色 | 激活码上限由 MT 全局配置 + 机构配置控制 |
| 统一 API 与数据库 | 机构、人员、角色、分组、模板、流程、打分规则、字典、报送单、审核记录、附件元数据 | 所有业务表带 `org_id`；预留 `tenant_id` |
| 两级配置模型 | 平台默认配置 → 机构开通时初始化 → 机构可调整 | MT 全局配置是"出厂默认值"，机构详情 / 客户管理端改的是本机构配置 |
| 文件与附件服务 | 图片 / 文件上传、压缩、访问鉴权 | H5 拍照上报、PC 附件预览都依赖 |
| 状态机与流水 | 报送状态：待审核 → 审核中 → 已采纳 / 被驳回，被驳回可修改重交；每个动作落一条流水 | **无草稿态、无撤回**；3.0 的统计、考核、日志直接消费这份流水 |
| 审核打分落库 | 每次审核记录节点、审核人、结论、驳回原因、得分、时间 | 3.0 考核的数据源，口径须在 1.0 定稿 |
| 环境配置与独立部署 | 四端各自登录、各自部署；API 地址按环境注入 | 不依赖门户 |

### 3.8 1.0 验收标准

- MT 用企业微信扫码登录，新建并开通一个机构，该机构自动带上平台默认的模板、流程、打分规则、激活码上限和字典；
- 客户管理员微信扫码登录，调整本机构的模板与审核流程，建立组织、角色、人员分组；关联两个机构的账号可切换，数据随之切换；
- 一线人员在微信内用激活码完成激活绑定，再次打开免登录；
- H5 按模板完成一次带图片附件的报送，PC 端也能用同一模板上报；
- 审核按配置的流程逐级流转：H5 / PC 审核员通过或驳回（驳回必填原因），客户管理端采纳并打分；
- 上报人在"我的报送"看到已采纳 / 被驳回及驳回原因，被驳回的可修改重交，待审核和被驳回的可删除；
- 每一次状态变化和打分在数据库中都有流水（为 3.0 的统计、考核、日志铺路）；
- 关闭前端 mock 后系统仍可正常使用。

## 四、2.0 功能清单：审核提效与数据沉淀

### 4.1 版本目标

在 1.0 闭环之上，让审核更快、让通过的数据沉淀为可复用资产，并把 AI 接入上报和审核主流程。现有客户管理端原型中的数据仓库、批量匹配、转办等能力在本版本落地。

### 4.2 数据仓库（客户管理端）

| 功能 | 说明 | 优先级 |
| --- | --- | --- |
| 仓库管理 | 仓库的新建、编辑、启停、删除，按分类与可见范围（全机构 / 指定人员 / 仅本人）管理；停用仓库排在列表末尾 | P0 |
| 数据归属 | 一条数据可同时属于多个仓库；迁移、移出只影响当前仓库 | P0 |
| 审核时入库 | 审核详情选择仓库，审核通过后自动加入；批量审核时可勾选哪些数据入库 | P0 |
| 审核记录入库 | 已采纳的审核记录可批量加入仓库 | P0 |
| 仓库数据操作 | 检索筛选、批量迁移、批量移出、数据导出 | P0 |
| 转办 | 仓库数据转办到指定机构 / 部门，记录转办状态并可再次转办 | P1 |

### 4.3 审核提效

| 功能 | 说明 | 优先级 |
| --- | --- | --- |
| 批量匹配与批量裁决 | 按同源链接 / 同地址聚类，批量通过或批量驳回，可分别打分 | P0 |
| 重复与首发识别 | 判定首发 / 重复并给出依据，审核时可人工改判 | P0 |
| 转办（H5 / PC） | 审核环节转办到其他节点或机构 | P1 |
| 驳回原因字典 | 驳回类型标准化，H5 / PC / 客户管理端共用 | P1 |
| 快捷键审核 | 全键盘通过 / 驳回 | P2 |

### 4.4 AI 能力

| 功能 | 说明 | 优先级 |
| --- | --- | --- |
| OCR 识别 | 证件、材料字段自动提取并回填表单 | P0 |
| AI 生成报送正文 | 根据标题与素材生成正文，作为表单预填，仍需提交审核 | P0 |
| 同类事件聚类 | 新报送与存量事件的相似度提示 | P1 |
| AI 辅助审核 | 风险提示与建议结论，最终裁决由人工确认 | P1 |
| AI 调用配额与审计 | 按机构计量调用量，所有调用走服务端 | P1 |

### 4.5 组织权限与移动端增强

| 功能 | 说明 | 优先级 |
| --- | --- | --- |
| 数据范围细化 | 本人 / 本机构 / 本机构及下级 / 全部；按钮级权限 | P0 |
| 人员批量导入导出 | Excel 导入导出、调岗、离职封存 | P1 |
| 客户管理端报送台账 | 管理员查看本机构全部报送、代录 | P1 |
| 公众号入口与二维码体系 | 公众号菜单进入 H5；上报码生成、失效、来源统计；二维码配额 | P1 |
| 多模态附件 | 语音、视频、链接采集上传 | P1 |
| 弱网与定位 | 已提交报送的离线排队重传、GPS 定位与水印 | P2 |
| 备用登录方式 | 账号密码 / 短信验证码，用于微信不可用的场景 | P2 |

### 4.6 2.0 验收标准

- 审核时选择仓库，通过后数据出现在对应仓库；同一数据可属于多个仓库，迁移、移出互不影响；
- 同源多条报送可一键批量裁决，并给出首发 / 重复判定；
- 上传一张证件照片，OCR 自动回填字段；AI 生成正文后可直接提交审核；
- 仓库数据可转办、可导出；
- 所有 AI 调用走服务端，前端不含任何密钥。

## 五、3.0 功能清单：首页 / 统计 / 考核 / 日志 / 消息

### 5.1 版本目标

把 1.0、2.0 积累的报送流水、审核打分、组织归属变成管理资产：**数据能看、人员能考、行为可审计、信息能触达**，并具备商业化交付能力。

> 前提：这些模块的数据从 1.0 起就已产生。3.0 做的是查询、聚合、展示与规则计算，不是从零开始记数据。

### 5.2 首页工作台（四端）

| 端 | 功能 | 优先级 |
| --- | --- | --- |
| H5 | 待审核 / 被驳回待办计数、快捷入口、最近报送 | P0 |
| PC | 待办概览、我的报送与审核概况、快捷入口 | P0 |
| 客户管理端 | 审核数据统计卡片、待办积压、机构报送概况 | P0 |
| MT | 平台概览：机构数、人员数、报送总量、活跃度 | P0 |

### 5.8 3.0 验收标准

- 四端首页展示真实待办与概况数据；
- 按机构统计当月报送量、采纳率、平均审核时长，可逐条下钻核对；
- 配置一条月度考核规则，系统基于审核打分自动算出人员排名并可下钻；
- 任取一条报送，可查到从提交到采纳的全部操作日志；
- 发布一条定向公告，目标人员收到站内信并回传已读。

## 九、关键风险与待决策问题

| # | 问题 | 影响 | 建议 |
| --- | --- | --- | --- |
| 1 | **1.0 全部依赖微信 / 企微登录** | 公众号、开放平台网站应用、企业微信应用的申请与认证有周期；测试环境需可回调的域名 | 立项即启动申请；开发期提供仅测试环境可用的模拟登录 |
| 2 | **审核结果没有消息推送** | 1.0 无消息中心，上报人只能在"我的报送"里看到结果 | 1.0 接受"列表状态 + 驳回原因"作为闭环；如需提醒，可提前做一条微信模板消息 |
| 3 | **打分口径必须在 1.0 定稿** | 3.0 考核直接使用打分，口径后改则历史数据无法回溯 | 1.0 锁定打分档位、计分节点（仅终审 / 每个节点）和数据字典 |
| 4 | **两级配置的覆盖规则** | MT 全局配置改动后，已开通机构是否同步不明确 | 约定：全局配置只影响新开通机构；已开通机构由机构详情或客户管理端单独维护 |
| 5 | **配置在 MT 机构详情与客户管理端两处可改** | 两处同时修改会冲突，责任不清 | 明确分工：MT 负责开通时初始化与兜底，日常维护在客户管理端；双方修改都写流水 |
| 6 | **切换机构的数据隔离** | 一个账号关联多机构，切换后的缓存与权限若处理不当会串数据 | 服务端以当前机构为上下文校验每个请求；前端切换后清空缓存 |
| 7 | **PC 与客户管理端模块重叠** | 审核列表、详情两端各做一遍 | 共用列表与详情组件，按角色裁剪功能 |
| 8 | **日志埋点从 1.0 启动** | 不埋点则 3.0 日志中心无历史数据 | 1.0 所有写操作统一走埋点中间件，界面 3.0 再做 |
| 9 | **原型中已有 2.0 / 3.0 能力** | 数据仓库、批量匹配、转办、首页、统计在原型中可见，1.0 交付时需要隐藏 | 按版本用功能开关控制菜单与按钮，不删代码 |
| 10 | 后端人力与工期 | 1.0 同时承担登录、多机构、两级配置，比 v0.1 更重 | 先评估后端人力，必要时把客户管理端"人员分组""数据字典"放到 1.0 末段 |
| 11 | 产品名不统一（速报 / 速豹 / 点点速报） | 交付物与品牌混乱 | 统一对外名称后修正各端标题 |

## 十、一句话总结

1.0 按需求功能确认单交付"多机构 + 微信登录 + 两级配置 + 报送审核打分"的完整闭环，先做 MT 与客户管理端（P0），再做 H5 与 PC（P1）；2.0 落地数据仓库、批量匹配、转办与 AI，让审核提效、数据沉淀；3.0 用 1.0 起累积的流水与打分，做四端首页、统计、考核、日志和消息公告，并具备商业化能力。

**首页、统计、考核能安全放到 3.0 的前提是：状态流水、审核打分、组织归属、操作埋点在 1.0 就开始记录。**
